# Round 2 dataset — tool selection with "none of these"

Every item is one request and 2–10 candidate tools; the gold is one tool id, or `null` when none of the tools fits
(the `X` label). The model answers with a single label token (`A`–`J` or `X`). Train 14 513, validation 3 524,
test 10 013 items.

## Two kinds of row

| file | rows | what is in a row |
|---|---|---|
| `items_hu.jsonl.gz` | 10 176 | **full rows** — request, history, options with descriptions, gold, meta. The Hungarian layers: MASSIVE hu-HU mapped onto our general tool catalogue (train / val / test), the catalogue's own generated Hungarian requests (test), EU-180k Hungarian conversations (train) |
| `items_ref.jsonl.gz` | 17 874 | **reference rows** for items built from public benchmarks — BFCL v3 (incl. live), When2Call, xLAM: id, source, split, the number of history turns, the option ids and the gold as pseudonyms, the non-text meta, and the sha256 of the converted row |

Why reference rows:

- **BFCL** is a test benchmark; its rows are not republished in any training-usable form (pre-registered, round-2
  protocol §8). The When2Call test set is built from BFCL-live, so it is treated the same way.
- **xLAM** (and the When2Call train set, whose tools come from xLAM) is CC-BY-4.0 behind a click-through gate, and
  part of it was generated by DeepSeek-V2-Chat. The generator's licence check is still open, so its rows are not
  republished here.

The reference rows are rebuilt from the upstream files with `code/kor01/eszkozok/forras_konvertal.py` and
`osszeallit.py`; the upstream sha256 are in `corpus_manifest.json` (`upstream`). The per-row `sha256` is the
sha256 of the converted row as canonical JSON (`sort_keys`, no whitespace, UTF-8), so a rebuild can be checked
row by row. A clean-room rebuild has not been run.

## Pseudonyms

In reference rows, every tool name is replaced by `t_` + the first 12 hex digits of
`sha256("docai-evals/2026-10-09:" + name)`: option ids, gold, and the meta fields that hold a tool name
(`kivett_gold`, `potlas`, `soft`, `felulvizsgal`, `szinonim_csere`, `szinonim_jelzes`, `atnezes`). The xLAM cluster
key (a normalised request) is hashed the same way. The read-outs in `results/r01/readouts/` use the same pseudonyms, so
every metric is computed exactly as on the original rows (`code/verify_package.py`).

## Label review — who decided

The labels of the two scored Hungarian test layers were reviewed in full: T-hu (the reviewed MASSIVE subset, 593
items) and T-katalógus (636). The reviewer was a GPT-based agent, audited by a blind human spot check (300 unchanged
labels and the agent's 70 corrections; 87 % of the corrections confirmed). A sample of the validation set went
through the same review. BFCL and When2Call gold labels are the benchmarks' own and were not reviewed; the
remaining MASSIVE test items (`T-hu-maradek`) are descriptive only and not in the scored pool.

`meta.atnezes` is present where the review changed something, and `meta.atnezes.forras` says who decided
(pre-registered, round-2 protocol §8):

| `forras` | meaning | what it changed |
|---|---|---|
| `gepi+dani` | machine decision, confirmed by a human | label corrections (`muvelet: javit`) |
| `dani` | human decision | ambiguity flags, one correction |
| `gepi` | machine decision only | ambiguity flags (`muvelet: ketertelmu`) — these items are not scored |

Every label correction is human-confirmed. Labels the review left unchanged carry no field. The estimated residual
noise is 1.2 % (upper 95 % bound 2.4 %), above the pre-registered 2 % gate; the results report it as a limitation.

## Other files

- `catalog/tools.json` — the general tool catalogue (62 tools; name, Hungarian and English description, JSON
  parameter schema). Our own work, Apache-2.0.
- `catalog/massive_mapping.json` — MASSIVE intent → catalogue tool.
- `layers.json` — inputs of two descriptive layers. `T-uj-eszkoz`: BFCL and When2Call test items whose tools are
  new to training — the gold name is not among the training tools and the gold description's highest bge-m3 cosine
  to a training tool is below 0.85 (for an X item, every option). `near_duplicate_requests`: test items whose
  request has a training request at bge-m3 cosine ≥ 0.95; `T-hu-dedup` is T-hu without them.
